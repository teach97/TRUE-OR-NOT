# True or Not 20분 발표 스크립트

README와 최신 아키텍처·배포·작업현황 문서를 바탕으로 발표 대본을 정리했습니다. 전체 시간은 **20분**이며, **발표 8분·서비스 시연 10분·질의응답 2분**으로 구성합니다. 대괄호 안은 발표자용 진행 메모이며 읽지 않습니다.

## 발표 전 준비

- [배포된 서비스](https://true-or-not-ten.vercel.app)에서 접속·검증이 되는지 미리 확인합니다. 접속 비밀번호나 키는 화면·터미널에 노출하지 않습니다.
- 시연 질문은 아래 예문 3번과 5번을 우선 사용합니다. 실제 시연 전에 판정 결과와 YouTube 출처가 나타나는지 확인합니다.
- 응답이 지연될 경우를 대비해 결과 화면을 준비합니다. 준비 화면은 실시간 결과와 구분해 소개합니다.
- 아키텍처 그림, 결과 대시보드, 검토한 출처·YouTube 패널을 발표 전에 열어 둡니다.

## 발표 진행 방식

- 0:00–8:00 전체 설명과 역할 소개는 주 발표자인 본인이 진행합니다.
- 8:00–18:00 시연에서는 담당자가 자기 파트를 직접 조작하고 설명한 뒤 다음 담당자에게 넘깁니다.
- 대괄호의 `[전체 발표: 본인]`, `[시연: 이름·역할]`, `[전체 발표 복귀: 본인]` 표시는 진행자를 구분하기 위한 메모이며 읽지 않습니다.

## 발표 대본 · 8분

### 0:00–1:30 | 프로젝트 소개와 문제

안녕하세요. 저희 팀 프로젝트 **True or Not**을 소개하겠습니다.

온라인 기사나 게시물에는 사실 주장뿐 아니라 의견과 예측도 함께 들어 있습니다. 검색 결과를 몇 개 확인하는 것만으로는 주장이 원문과 일치하는지, 인용에 필요한 조건이 빠지지 않았는지 판단하기 어렵습니다.

True or Not은 사용자가 확인하고 싶은 내용을 입력하면 주장을 나누고, 관련 출처와 원문을 찾아 판정과 함께 보여주는 웹 서비스입니다. 결과를 참이나 거짓으로만 단정하지 않고, 근거가 부족하거나 확인할 수 없는 내용은 그 상태를 함께 표시하는 것이 핵심입니다.

오늘 발표에서는 기능 설명에 더해, 팀원별로 나누어 작업한 기능을 어떻게 연결하고 병합했는지 중심으로 말씀드리겠습니다.

### 1:30–3:00 | 역할별 작업과 통합·병합

[전체 발표: 본인]

팀원별 담당 역할은 김훈 팀장이 PM과 백엔드, 전소예 팀원이 백엔드, 이성우 팀원이 QA, 백승준 팀원이 프런트엔드입니다. 역할과 통합 과정은 제가 이어서 설명하고, 시연에서는 각 담당자가 자기 분야의 화면과 기능을 직접 보여드리겠습니다.

저희는 화면 만들기, 사실 확인, 자료 찾기, 서버 만들기, 테스트와 문서 작성을 나눠 맡았습니다. 각자 만든 기능이 함께 잘 작동하도록 입력과 결과를 주고받는 방법을 맞추고, 주장과 출처를 연결해 하나의 서비스로 합쳤습니다.

예를 들어 프런트엔드는 진행 상태와 결과를 화면에 표시하고, 백엔드는 검증 상태와 근거를 같은 계약에 맞춰 전달해야 합니다. 계약이 어긋나면 화면에는 결과가 있어도 해당 출처가 어느 주장에 연결되는지 틀릴 수 있어, 기능을 합친 뒤 경계와 결과 형식을 함께 확인했습니다.

코드 변경을 깃허브에 올리면, 깃허브가 자동으로 테스트하고 서비스가 만들어지는지 확인합니다. 당시 그 검사를 통과했습니다. 실제 검색과 배포는 따로 확인해야 합니다.

### 3:00–4:30 | 검증 흐름과 화면 기능

검증은 크게 다섯 단계로 진행됩니다. 먼저 입력에서 최대 세 개의 주장을 추출하고, 검색 단계에서 일반 출처와 관련 YouTube 영상을 찾습니다. 다음으로 후보 페이지의 원문을 읽고, 검증 단계에서 주장과 원문 인용을 대조합니다. 마지막 단계는 결과 형식을 확인하고 판정과 근거를 화면에 전달합니다.

여기서 마지막 단계 이름은 synthesizing이지만, 현재 메인 검증에서는 답변을 만들기 위한 추가 LLM 호출을 하지 않습니다. 검증된 판정과 근거를 정리해 결과 계약에 맞추는 단계입니다.

화면에는 종합 팩트 점수와 주장별 점수가 표시됩니다. 여러 주장이 있을 때는 주장 카드를 선택해 해당 주장과 연결된 출처를 따라갈 수 있습니다. YouTube 정보·댓글 패널은 영상 정보를 참고 맥락으로 보여주며, 댓글이나 영상 정보 자체를 판정 근거와 동일하게 취급하지 않습니다.

### 4:30–6:30 | 배포와 QA 범위

배포 구조는 브라우저와 Next.js 프런트·프록시가 Vercel에 있고, FastAPI 백엔드와 PostgreSQL은 Render에 있는 형태입니다. 브라우저가 데이터베이스에 직접 접속하지 않고, 백엔드가 DB 연결을 담당합니다. 대화 저장은 별도 선택으로 제공되며, 외부 서비스 전송 동의와 대화 저장 동의는 서로 다른 선택입니다.

QA에서는 프런트엔드와 백엔드 테스트, 타입 검사, 프로덕션 빌드 등을 자동으로 확인합니다. 실제 배포에서도 기본 공개 연결과 검증 요청을 확인한 기록이 있습니다. 다만 자동 검사는 실제 모델·검색 공급자의 모든 응답을 검증하지 않으며, 대화 전체 저장·복원 수용 시험과 부하 검증은 별도 확인 범위로 남아 있습니다.

그래서 발표에서도 테스트 통과와 실제 서비스 확인을 구분해 말씀드리겠습니다. 확인하지 않은 항목을 완료됐다고 표현하지 않는 것도 프로젝트의 작업 기준으로 삼았습니다.

### 6:30–8:00 | 요약과 시연 안내

[전체 발표: 본인]

정리하면 True or Not은 주장만 판정하는 서비스가 아니라, 판정이 어떤 원문과 연결되는지 사용자가 따라가며 확인하도록 돕는 서비스입니다. 또한 이번 작업의 중요한 과정은 프런트엔드, 검증 로직, 검색·백엔드, QA처럼 나누어 진행한 결과를 공통 계약에 맞춰 통합하고, PR과 검증 절차로 병합한 것입니다.

이제부터는 시연 담당자들이 각자 맡은 부분을 직접 조작하며 설명하겠습니다. 먼저 달의 위상에 관한 오해를 YouTube 출처와 함께 살펴보고, 다음으로 화성의 위성에 관한 사실을 확인하겠습니다. 결과를 볼 때는 판정뿐 아니라 주장과 출처가 어떻게 연결되는지도 함께 봐주시면 좋겠습니다.

## 복합 주장 예문 · 참과 거짓이 섞인 문장

아래 문장은 각각 한 문장 안에 두 가지 사실을 담았습니다. 입력할 때 “두 내용을 나눠 검증해줘”를 덧붙이면, 주장을 분리해 각 부분의 판정을 확인할 수 있습니다.

| 입력 예문 | 참인 내용 | 거짓인 내용 | 참고 출처 |
|---|---|---|---|
| 금성은 태양계에서 가장 뜨거운 행성이며, 태양에 가장 가까운 행성이다. 두 내용을 나눠 검증해줘. | 금성은 태양계에서 가장 뜨거운 행성입니다. | 태양에 가장 가까운 행성은 금성이 아니라 수성입니다. | [NASA: 금성](https://science.nasa.gov/venus/venus-facts/), [NASA: 수성](https://science.nasa.gov/mercury/facts/) |
| 달은 태양빛을 반사해 빛나며, 달의 위상 변화는 지구 그림자가 달을 가리기 때문에 생긴다. 두 내용을 나눠 검증해줘. | 달은 태양빛을 반사합니다. | 일반적인 달의 위상 변화는 지구 그림자 때문이 아니라, 달을 비추는 태양빛을 지구에서 보는 방향이 달라지기 때문에 생깁니다. | [NASA: 달빛](https://science.nasa.gov/moon/moonlight/), [NASA: 달의 위상](https://science.nasa.gov/resource/phases-of-the-moon-2/) |
| 화성에는 포보스와 데이모스라는 두 위성이 있으며, 두 위성은 지구의 달보다 크다. 두 내용을 나눠 검증해줘. | 화성에는 포보스와 데이모스라는 두 위성이 있습니다. | 두 위성은 지구의 달보다 작습니다. | [NASA: 화성의 위성](https://science.nasa.gov/mars/moons/), [NASA: 위성 크기 비교](https://science.nasa.gov/resource/illustration-comparing-apparent-sizes-of-moons/) |

발표에서는 문장 전체를 하나의 참·거짓으로 뭉뚱그리지 않고, 각각의 사실을 분리해 판정하는지 보여줍니다. 실제 서비스가 이 예문을 몇 개의 주장으로 추출하는지는 시연 전에 확인합니다.

## 시연 지연 시 진행 요령

실시간 응답이 지연되면 진행 화면을 보이며 추출·검색·원문 읽기·검증 단계를 설명합니다. 준비한 결과 화면으로 전환할 때는 사전 실행 결과라고 밝히고, 현재 실시간 결과처럼 소개하지 않습니다. 제한 시간 안에 응답이 없으면 해당 상태를 설명하고 질의응답으로 넘어갑니다.
