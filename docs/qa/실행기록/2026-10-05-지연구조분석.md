## 현재 구조와 확인 근거

기준 코드는 `32d63a8`입니다. Graphify의 `verify synthesis structured workflow runtime stream` DFS 탐색으로 workflow·runtime·streaming·provider·합성 경로를 찾고 실제 소스와 대조했습니다. 그래프 출력은 169개 노드 중 예산 내 32개만 표시하므로 전체 경로의 완전성 증거로 사용하지 않습니다. 용어집·관련 ADR 파일은 파일 목록에서 발견하지 못했습니다.

```text
읽은 원문 → 판정 LLM → 서버 인용/조건 검사 → 판정 preview
                ↓ 판정·근거 + 원문을 다시 입력
            합성 LLM → 서버 인용 검사 → 최종 답변
```

| 단계 | 모델에 전달하는 자료 | 생성·검사하는 결과 |
|---|---|---|
| 판정 | 사실/불명확 주장, 주변 문장, 기사 정보, 계산값, verified 출처별 앞 6,000자 | 점수·판정·요약·확인/미해결 내용·직접 인용·번역. 서버는 원문 일치·비교 조건·근거 충돌을 검사하고 판정을 조정합니다. |
| 합성 | 질문·확인 초점·판정 결과·근거 인용, 비-YouTube verified 출처별 앞 6,000자(최대 6개) | 개요·최대 4절/절당 3항목·결론과 문단별 인용. 서버는 인용의 출처/본문 일치를 검사합니다. |

- 근거 코드: `backend/verification.py`의 `verify_claims`/`ground_judgments`, `backend/answer_synthesis.py`의 `_synthesis_input`/`synthesize_answer`, `backend/workflow.py`의 직렬 단계, `backend/streaming.py`의 preview/result 경계입니다.
- 원문은 다시 HTTP로 가져오는 것이 아니라 별도 LLM 입력으로 다시 전달합니다. 두 단계 모두 자료 선택과 서술·인용 구성에 관여할 여지가 있지만 서로 목적이 다르므로 전부 무의미한 중복이라고 단정하지 않습니다.
- `_limit_sections_to_source_breadth`는 생성 후 절을 삭제합니다. 생성된 전체 답변을 받기 전에는 이 제한이 적용되지 않습니다.
- 계약의 허용 최대치는 개요·결론과 4×3개 항목, 즉 14개 문단입니다. 각 문단 최대 3개 인용으로 총 42개 인용 항목을 허용하고 인용마다 최대 2,000자입니다. 실제 생성량의 관찰값이 아니라 정적 계약 상한입니다.
- [직전 실측](2026-10-05-지연측정.md)은 판정 입력/출력 17,329/3,175토큰·22.51초, 합성 입력/출력 8,974/16,000토큰·64.96초 및 length 실패입니다. 입력량만으로 전체 지연을 설명하지 않으며 보고된 출력의 추론/본문 구성도 미확정입니다.

| 후순위 | 판정과 답변 초안을 같은 LLM 호출로 생성 | 두 호출을 하나로 줄일 수 있지만 서버의 판정 조정/재탐색 후 초안을 무효화하고 판정·서술·인용 정합을 검증해야 합니다. 생성 작업 증가로 통합 호출 자체가 길어질 수 있어 기존 시간 합계만큼의 절감을 보장하지 않습니다. |

예측·의견은 현재 `verify_claims`에서 사실 판정 대상이 아니므로 기존 evidence가 비어 있을 수 있습니다. AGI 시점 같은 질문에서 합성 입력을 사실 판정의 인용만으로 제한하면 필요한 전문가 발언·예측 시점·조건이 사라질 수 있습니다. 예측/맥락용 발췌를 따로 확보하거나 해당 입력은 기존 경로를 유지해야 하며, 예측을 사실 판정으로 바꾸는 방식으로 해결하지 않습니다.

판정과 합성을 현재 의존성 그대로 독립 병렬 호출하는 안은 권장하지 않습니다. 합성은 서버 검증·판정 조정·1회 재탐색을 마친 결과에 의존합니다. 연결 재사용·캐시는 후속 후보이나 이번 65초 구간의 원인이라는 계측 증거는 없습니다.
