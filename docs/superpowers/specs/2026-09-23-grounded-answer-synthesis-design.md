# 근거 기반 종합 답변 및 인라인 출처 설계

- 상태: 사용자 검토 대기. 구현 전 설계안입니다.
- 작성일: 2026-09-23
- 범위: 검색 개선 5단계

## 문제와 목표

현재 시스템은 주장을 추출하고 검색 출처의 본문을 읽은 뒤, 확인 가능한 주장별 판정·점수·인용을 반환합니다. 프론트엔드의 채팅 답변은 첫 번째 사실 또는 불명확 주장 하나의 요약과 판정 정보를 문장으로 조합합니다. 예측 주장은 `not_checkable`로 유지되며, 찬성·반대 전망을 종합한 답변은 생성하지 않습니다. 인용은 답변 문장 안이 아니라 별도 근거 패널에 표시됩니다.

이번 단계의 목표는 검증 후 별도의 LLM 호출을 추가해 읽을 수 있는 원문에 한정한 종합 답변을 만드는 것입니다. 답변에는 짧은 개요, 관련 관점과 불확실성, 결론을 포함하고 각 실질적 문단을 실제 원문 인용 및 출처 링크에 연결합니다. 예측은 확정된 사실처럼 표현하지 않으며, 기존 사실 판정과 점수는 그대로 보존합니다.

## 승인된 접근

기존 추출·검색·원문 읽기·사실 검증 뒤에 독립된 종합 단계를 추가합니다. 기존 검증 프롬프트에 전망 합성을 합치지 않습니다. 이 방식은 기존 검증 계약을 유지하고, 예측 질문도 같은 근거 경계 안에서 별도 답변으로 다룰 수 있습니다. 요청마다 종합 LLM 호출이 하나 늘어 응답 시간과 비용이 증가합니다.

## 데이터 흐름

1. `extracting`: 사용자 문장에서 최대 3개 주장을 추출하고 검색어를 만듭니다.
2. `searching`: 기존 검색 공급자가 반환한 후보를 순서 보존·중복 제거 규칙으로 제한합니다. Google 자연 검색 순위로 간주하지 않습니다.
3. `reading`: 접근이 허용된 공개 페이지 본문을 읽습니다. YouTube 댓글은 LLM에 전달하지 않습니다.
4. `verifying`: 확인 가능한 사실 주장만 기존 검증 경로로 판정하고 정확 인용을 원문과 대조합니다. 의견·예측의 `not_checkable` 상태를 유지합니다.
5. `synthesizing`: 사용자 질문, 확인된 주장·근거, 원문을 보유한 출처만 별도 모델 호출에 전달하여 구조화된 답변을 생성합니다.

스트림에는 `synthesizing` 진행 이벤트를 추가하고 검증 완료 뒤 최종 응답을 보냅니다. 합성 결과의 모델 정보는 `answer`에 기록하여 기존 최상위 검증 모델 메타데이터와 구분합니다.

## 응답 계약

기존 `FactCheckResult`에 `answer` 필드를 추가합니다. 개념적 구조는 다음과 같습니다.

```text
answer:
  status: grounded | insufficient_evidence
  overview: AnswerBlock | null
  sections: AnswerSection[]
  conclusion: AnswerBlock | null
  model: string | null
  reasoning: max | high | null

AnswerBlock:
  text: string
  citations: [{ sourceId: string, quote: string }]

AnswerSection:
  kind: supporting | counter | uncertainty | context
  title: string
  items: AnswerBlock[]
```

`grounded`일 때 개요와 결론을 제공하며 실질적 블록에는 인용이 필요합니다. `insufficient_evidence`는 섹션을 비우고 결론을 생략할 수 있으며, 성공한 합성 provider가 없으면 모델 메타데이터는 `null`입니다. 세부 상한은 기존 계약 스타일에 맞춰 고정합니다: 답변 문단 최대 1,200자, 섹션 최대 4개, 섹션별 항목 최대 3개, 문단별 인용 최대 3개, 인용문 최대 2,000자입니다. 불필요한 빈 섹션은 반환하지 않습니다. 현재 JSON 계약과 Node 클라이언트 검증을 동시에 갱신합니다.

## 근거·표현 정책

- 종합 단계에는 `sourceTexts`가 존재하고 `accessStatus=verified`인 출처만 근거 후보로 전달합니다. 검색 스니펫, 출처 제목만 있는 YouTube 결과, YouTube 제목·공개 댓글은 종합 근거에서 제외합니다.
- 모든 실질적 답변 블록은 하나 이상의 출처 인용을 포함해야 합니다. 각 인용의 `sourceId`는 실제 출처에 연결되어야 하고 `quote`는 해당 출처 본문에서 정확히 일치하는 연속 문자열이어야 합니다.
- 인용이 없는 단정, 존재하지 않는 출처 ID, 원문과 일치하지 않는 인용은 통과시키지 않습니다. 기존 제공자 폴백을 통해 재시도하고, 모든 제공자가 실패하면 검증된 기존 결과를 보존한 채 `insufficient_evidence` 답변으로 마무리합니다.
- 예측 답변은 전망·조건·불확실성을 서술하며 사실의 참·거짓으로 재분류하지 않습니다. 예측 확률이나 전문가 다수 의견을 원문이 명시하지 않으면 만들어 내지 않습니다.
- 상반된 관점은 실제 수집 원문이 뒷받침할 때만 각각 표시합니다. 찬반을 형식적으로 같은 수로 맞추거나 출처 개수만으로 합의를 추론하지 않습니다.
- 기존 주장 점수, 판정, 정확 인용, 경고를 대체하지 않습니다. 종합 답변이 실패해도 확인된 주장별 판정은 가능한 한 반환합니다.

## 화면

현재 채팅의 한 줄 합성 답변을 구조화된 답변 렌더러로 바꿉니다. 답변은 `AI 개요` 제목, 개요 문단, 근거가 있는 관점 섹션, 불확실성, 결론 순으로 표시합니다. 인용 칩은 연결된 출처 제목을 접근 가능한 이름으로 보여 주고 해당 출처 URL을 엽니다. 선택 주장·점수·상세 인용 패널은 유지합니다. 로컬 합성 데모와 오류 메시지는 실제 API 답변과 계속 구분합니다.

## 실패 처리와 개인정보

- 원문 출처가 없거나 모두 읽지 못하면 근거 없는 장문을 생성하지 않고 짧은 근거 부족 답변을 반환합니다.
- 구조가 잘못됐거나 인용 grounding을 통과하지 못한 모델 응답은 사용자에게 노출하지 않습니다. 모든 제공자 실패 시 안전한 제한 응답과 기존 검증 데이터를 반환합니다.
- 종합 LLM 호출에 기존 사용자 동의 범위와 서버 측 provider 키 설정을 적용합니다. 새 키나 저장소는 추가하지 않습니다.
- 검증 원문과 종합 답변을 새로 영속 저장하지 않습니다. 기존 JSON 내보내기 동작과 YouTube API 데이터 제외 정책을 유지합니다.

## 비목표

- Google 자연 검색 SERP의 직접 스크래핑 또는 순위 API 도입
- YouTube 자막·영상·답글 수집 또는 공개 댓글을 사실 근거·LLM 입력으로 사용하는 일
- 사용자 검증 이력의 서버 저장, 새로운 사용자 인증, 새로운 provider 도입
- 근거가 뒷받침되지 않는 정확한 미래 확률이나 출처 간 합의율 계산

## 구현 파일 후보

- 백엔드: `backend/workflow.py`, `backend/runtime.py`, `backend/contracts.py`, 스트림 단계가 정의된 `backend/streaming.py`, 종합 프롬프트·근거 대조 모듈 및 해당 단위·그래프·API 테스트
- 프론트엔드: `app/lib/fact-check-contract.ts`, `app/components/fact-check-client.ts`, `app/components/fact-check-dashboard.tsx`, `app/globals.css`, 기존 채팅 답변 테스트
- 인계: `HANDOFF.md`의 5단계 상태 및 실제 검증 결과

구현 전 현재 파일과 테스트 경계를 다시 확인하고, 코드 변경 전 RED 테스트를 먼저 추가합니다. 기존 개발 서버를 중단하지 않으며 live LLM 호출 없이 mock 기반 회귀를 기본 검증으로 합니다. 실제 provider 호출은 비용·자격 증명 설정을 확인한 별도 검증으로 구분합니다.

## 승인 기준

1. 전망 질문에 대해 사실 판정과 별개의 한국어 개요·근거 있는 관점·불확실성·결론이 표시됩니다.
2. 답변에 노출되는 모든 인용 칩은 실제 `verified` 출처와 원문에서 정확히 찾은 인용 문자열에 연결됩니다.
3. 모델이 지어낸 URL·출처·인용, 검증되지 않은 검색 스니펫, YouTube 댓글이 종합 답변에 유입되지 않습니다.
4. 예측의 기존 `not_checkable` 판정이 유지되고 근거가 부족할 때는 과장된 결론을 만들지 않습니다.
5. 기존 사실 판정·인용·오류·취소·provider 폴백 회귀가 유지됩니다.
6. 모의 `AGI는 2030년 안에 오나?` 회귀에서 양쪽 전망, 불확실성, 실제 본문에서 grounding된 클릭 가능 인용을 확인합니다.
7. 백엔드 전체 테스트, 프론트 Node 테스트, TypeScript 검사 및 가능한 범위의 빌드가 통과하고 결과를 인계 문서에 기록합니다.
