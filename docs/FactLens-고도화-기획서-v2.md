## 1. 핵심 방향

**True or Not은 정답을 선언하는 서비스가 아니라, 주장과 근거를 추적·비교할 수 있게 하는 생활형 검증 도구입니다.**

사용자가 제공한 기사·댓글·텍스트에서 확인할 주장을 선택하고, 원문과 검색 근거를 나란히 제시합니다. 무엇이 확인되었는지, 무엇이 아직 불확실한지, 출처들이 같은 원자료를 반복하는지 구분하는 것을 핵심 가치로 삼습니다.

- 도메인: 생활·문화 중심의 일반 정보
- 대상: 기사와 온라인 주장에 의문을 가진 일반 사용자
- 핵심 단위: 기사 전체가 아닌 개별 주장
- 핵심 산출물: 원문 위치와 출처 인용이 연결된 주장별 검증 카드
- 성공 경험: 사용자가 판정 문구만 읽는 것이 아니라, 근거를 열고 결론의 한계를 이해할 수 있습니다.
- 비목표: AI 판정 정확도의 무근거 수치화, 작성자 평가, 전문 의사결정 대행

### 원안에서 강화한 사항

| 영역 | 원안 | 고도화 방향 |
|---|---|---|
| 주장 추출 | 자동 추출·분류 | 사용자 관심 범위 반영, 최대 3개 선택 확인, 원문 위치 보존 |
| 결과 분류 | 7개 결과 정의 | 처리 상태와 판정 분리, 겹치는 판정의 결정 규칙 추가 |
| 출처 중복 | 동일 원자료 그룹화 | 문서 중복과 근거 계보를 분리하고 불확실성 표시 |
| UI | 원문·주장·출처 구성 | 선택 상태 동기화, 모바일 흐름, 오류·접근성 기준 추가 |
| 개발 | 3일 일정 | 기능별 완료 조건, 외부 서비스 의존성, 축소 전략 추가 |
| 신뢰 | 출처 공개 | 인용 검증, 개인정보, URL 수집 보안, 데모 구분 추가 |

## 2. 문제 정의와 사용자 시나리오

온라인 텍스트에는 사실, 의견, 예측, 과장 및 오래된 정보가 섞여 있습니다. 여러 기사가 검색되어도 같은 발표를 재인용한 경우 독립적인 근거가 늘어난 것은 아닙니다. 수치가 다르더라도 비교 기간·지역·모집단 차이일 수 있으므로 불일치 자체를 오류로 단정해서는 안 됩니다.

| 사용자 상황 | 확인하려는 질문 | 제공할 결과 |
|---|---|---|
| 생활 물가 기사 | 어느 상품이 언제부터 얼마나 올랐는가? | 기간·대상·단위가 맞는 통계와 비교 |
| 정책 관련 댓글 | 확정된 정책인가, 검토 중인 안인가? | 발표일·시행일·정책 상태 구분 |
| 문화 행사 정보 | 올해 일정인가, 지난 행사 기사인가? | 행사 연도·지역·공식 공지 비교 |
| 과장된 온라인 문장 | 사실 부분과 해석이 무엇인가? | 사실 주장과 의견을 분리하고 한계 제시 |

의학·법률·투자의 개인별 판단 요청은 MVP 범위 밖임을 안내합니다. 사용자의 상태에 대한 진단이나 매매·법률 행동 권고를 생성하지 않습니다.

## 3. 제품 원칙

1. 검색 결과 부재를 거짓의 증거로 사용하지 않습니다.
2. AI가 생성한 설명을 원문 인용처럼 표시하지 않습니다.
3. 출처 개수와 독립적인 근거 수를 혼동하지 않습니다.
4. 공식 출처라는 이유만으로 모든 주장을 무조건 확인 처리하지 않습니다. 해당 주장과 직접 관련되는지 확인합니다.
5. 판정마다 기준 시각과 자료의 범위를 명시합니다.
6. 판정 근거가 부족하면 결론을 유보합니다.
7. 임의의 신뢰도 퍼센트·출처 품질 점수를 표시하지 않습니다.
8. 데모와 실제 검증을 입력·결과·다운로드에서 모두 구분합니다.
9. 입력 내용과 수집 페이지는 데이터로 취급하며, 그 안의 지시문을 도구 실행 지침으로 따르지 않습니다.
10. 접근 차단·로그인·유료벽은 우회하지 않고 대체 입력 경로를 제공합니다.

## 5. 상세 사용자 흐름

1. **입력**: URL 또는 텍스트를 선택하고 선택적으로 확인 요청을 작성합니다.
2. **원문 확보**: 서버가 읽을 수 있는 본문을 수집합니다. 실패 시 실패 이유와 붙여넣기 입력을 제공합니다.
3. **검증 후보 확인**: 최대 3개 주장을 원문 문장과 함께 보여줍니다. 의견·예측도 유형을 표시하되 검증 가능한 사실 요소만 검색 대상으로 삼습니다.
4. **선택**: 사용자가 원하는 주장을 선택합니다. 원문을 수정하면 이전 후보를 폐기하고 다시 추출합니다.
5. **실행**: 선택한 주장과 원문을 실행 시점의 스냅샷으로 고정합니다.
6. **탐색·비교**: 검색, 원문 확보, 출처 관계 확인, 조건 비교를 수행합니다.
7. **결과**: 각 주장의 판정·근거·한계와 접근하지 못한 자료를 보여줍니다.
8. **재확인**: 사용자에게 원문 출처 열기, 다른 주장 선택, 조건 보완 후 새 검증을 제공합니다.

실행 중 과거 결과를 선택해도 진행 중 요청의 주장이나 입력 스냅샷은 변경되지 않아야 합니다.

## 6. 주장 추출과 검증 계획

### 6.1 분류 체계

문장 유형과 검증 가능 여부를 분리합니다.

| 유형 | 처리 |
|---|---|
| 사실 주장 | 시점·대상·범위가 충분하면 검증 |
| 의견·가치 판단 | 검증 대상 아님. 포함된 사실 요소는 별도 주장으로 추출 가능 |
| 예측 | 미래 결과는 현재 확정하지 않음. 예측의 발표 여부는 별도 검증 가능 |
| 풍자 | 문맥이 분명할 때만 표시. 불명확하면 유형을 미확정으로 둠 |
| 유형 불명확 | 사용자에게 대상·기간 등 추가 조건 요청 |

사실 주장이지만 검색 근거가 없는 경우에는 ‘검증 대상 아님’이 아니라 ‘근거 부족’입니다.

### 6.2 주장 구조

주장별로 주체, 서술, 대상, 수치, 단위, 기간, 지역, 비교 기준을 구조화합니다. 원문에 없는 조건은 만들어 넣지 않습니다. ‘최근’, ‘올해’ 같은 상대 시점은 기사 발행일 등 해석 기준을 명시하고, 기준 날짜가 없으면 확인을 요청합니다.

- 추출 주장은 원문의 의미를 보존합니다.
- 원문 인용과 읽기 쉬운 정규화 문장을 별도 저장합니다.
- 후보가 많으면 확인 요청과 관련성이 높은 주장을 우선하되 일부만 분석했다는 사실을 표시합니다.
- 복합 주장은 가능하면 분리합니다. 분리하지 못한 경우 하위 조건별 확인·미확인 항목을 제공합니다.

### 6.3 검색 계획

주장별 핵심 개체·시점·수치를 이용한 검색, 공식 원자료 검색, 반박 또는 다른 조건의 자료 검색을 수행합니다. 검색 횟수와 본문 접근 수는 제한하여 비용과 대기 시간을 제어합니다.

## 7. 출처 정책과 독립성

| 출처 유형 | 역할 | 주의점 |
|---|---|---|
| 정부·공공기관·공식 통계 | 정책·수치의 주요 근거 후보 | 조사 범위·개정 여부·공표일 확인 |
| 논문·연구기관 보고서 | 전문 주장에 대한 근거 후보 | 연구 대상·방법·한계 및 철회 여부 확인 가능한 범위 표시 |
| 공식 발표·인터뷰·원문 기사 | 사건·발언의 직접 자료 | 발언 사실과 발언 내용의 진실성을 구분 |
| 관련 기사 | 비교·추가 탐색 | 원자료 인용과 독자 취재를 구분 |
| 위키피디아·나무위키 | 배경·검색 확장 | 핵심 판정의 단독 근거로 사용하지 않음 |
| 블로그·커뮤니티·댓글 | 유통 주장·경험·반응 확인 | 일반화의 근거로 사용하지 않음 |

출처 유형과 역할은 별개입니다. 검증 대상 기사도 직접 인터뷰의 원자료일 수 있으며, 공식 발표도 이해관계자의 주장일 수 있습니다.

### 독립성 처리

1. 추적 파라미터 제거 등 안전한 URL 정규화로 문서 중복 후보를 찾습니다. 문서를 구분하는 의미 있는 쿼리는 유지합니다.
2. 동일 본문·제목·공통 인용문·명시적 원자료 링크를 확인합니다.
3. 같은 원자료를 공유하면 `originGroupId`로 연결하고 관계를 확인한 이유를 저장합니다.
4. 제목 유사성만으로 같은 계보 또는 독립성을 확정하지 않습니다.
5. 관계가 불명확하면 `unknown`으로 표시합니다.
6. MVP에서는 ‘확인된 원자료 그룹 수’와 ‘관계 미확인 문서 수’를 표시합니다. 이를 보장된 독립 출처 수로 바꾸어 부르지 않습니다.

독립성이 충분히 확인되지 않으면 ‘독립 근거 부족’ 경고를 추가합니다. 출처 수가 많다는 이유만으로 판정 수준을 올리지 않습니다.

## 8. 판정 정책

### 8.1 결과 분류

| 코드 | 표시명 | 적용 기준 |
|---|---|---|
| mostly_supported | 대체로 확인됨 | 핵심 사실과 비교 조건이 직접 관련된 원문 근거와 일치하며 중대한 미해결 반박이 없음 |
| partially_supported | 일부만 확인됨 | 복합 주장의 일부만 확인되거나 일부 조건이 미확정 |
| missing_context | 맥락이 생략됨 | 표현 자체는 맞지만 조건·기간·범위 생략으로 의미가 달라짐 |
| conflicting_sources | 출처 간 내용이 다름 | 동일 조건으로 비교해도 관련 근거가 충돌하고 해소되지 않음 |
| insufficient_evidence | 근거 부족 | 직접 근거 미확보, 조건 불명확 또는 검색 범위 내 판단 불가 |
| not_checkable | 검증 대상 아님 | 의견·가치 판단·현재 확정할 수 없는 예측 등 |
| contradicted | 반박하는 근거 확인 | 같은 조건의 직접 근거가 핵심 주장을 반박하고 중대한 미해결 충돌이 없음 |

### 8.2 겹치는 경우의 결정 규칙

- 먼저 사실 검증 대상인지 확인합니다.
- 핵심 비교 조건을 맞출 수 없거나 유효 인용이 없으면 근거 부족으로 처리합니다.
- 기간·지역·단위를 맞추면 해소되는 차이는 출처 충돌로 단정하지 않습니다.
- 같은 조건의 유효 근거가 지지·반박으로 갈리면 충돌을 우선 표시하고 양쪽을 제시합니다.
- 중요한 조건 생략이 문제의 핵심이면 맥락 생략을 적용합니다.
- 복합 주장은 가능하면 분리하고, 분리 전 요약에는 일부 확인과 하위 결과를 제공합니다.
- 핵심 내용이 직접 반박되면 주변 사실 일부가 맞더라도 전체를 확인됨으로 처리하지 않습니다.

대표 판정은 하나만 사용하고 `warnings`에 조건 미확정·원자료 미확보·독립성 미확인 등을 함께 제공합니다. 판정은 정책 초안이며 QA 사례로 모호한 경계를 조정해야 합니다.

### 8.3 근거 충족 규칙

- 확인·부분 확인·맥락 생략·반박에는 실제 수집 원문에서 검증된 인용을 최소 하나 연결합니다. 이는 최소 형식 조건이며, 하나의 출처만으로 충분한지는 주장별로 판단합니다.
- 충돌 판정에는 상충하는 근거와 같은 조건으로 비교했다는 설명이 필요합니다.
- 검색 스니펫만 확보한 문서는 발견한 자료로 표시하며 결정적 원문 근거로 사용하지 않습니다.
- 원문에 없는 인용, 인용 대상 URL 불일치, 의미가 달라지는 문맥 절단이 발견되면 해당 근거를 제외하고 판정을 재평가합니다.
- 생성된 판정은 서버의 스키마·인용·참조 무결성 검사를 통과해야 노출합니다.

## 9. 화면 설계

### 9.1 정보 구조

**입력 → 주장 선택 → 원문·근거 비교 → 조건 보완**을 주 흐름으로 구성합니다. 관리용 대시보드와 가상 운영 지표보다 현재 문서 검증 작업을 우선합니다.

| 화면 영역 | 데스크톱 | 모바일 |
|---|---|---|
| 입력 | URL/텍스트 탭과 확인 요청 | 같은 순서의 세로 폼 |
| 원문 | 좌측 원문 뷰어 | 원문 탭 |
| 주장·판정 | 중앙 또는 주 콘텐츠 | 결과 탭의 주장 카드 |
| 근거 비교 | 우측 패널 또는 하단 표 | 출처 탭의 세로 카드 |
| 선택 상태 | 주장 ID로 패널 동기화 | 탭 전환에도 선택 유지 |

원문의 노란 강조는 ‘선택된 검증 대상’을 뜻하며 판정 색상과 구분합니다. 색만 사용하지 않고 문장 유형·판정 텍스트·아이콘을 병행합니다.

### 9.2 주장 카드

주장 원문, 유형, 판정, 한 줄 요약, 확인된 내용, 미확인 내용, 조건 차이, 인용 근거, 출처 작성일, 확인 시각, 한계를 표시합니다. 접힌 카드에도 판정과 핵심 한계를 남깁니다.

근거에는 다음을 함께 표시합니다.

- 원문 그대로의 인용과 별도로 작성한 해설
- 지지·반박·배경 정보 관계
- 수치·단위·기간·지역 및 비교 기준
- 출처 제목·기관·URL·발행일·수집 시각
- 원자료 그룹과 그룹화 사유 또는 관계 미확인

### 9.3 요약 지표

현재 실행 결과에서만 집계합니다: 선택한 주장 수, 판정 완료 수, 근거 부족 수, 열람 가능한 수집 문서 수, 실제 인용 문서 수, 1차 출처 문서 수, 확인된 원자료 그룹 수, 불일치 주장 수.

문서는 정규화된 식별자로 중복 제거하며, 하나의 문서가 여러 주장에 인용되어도 전체 문서 수에서는 한 번만 셉니다. 처리 실패와 근거 부족은 서로 다른 지표입니다. 평균 신뢰도와 임의의 출처 품질 퍼센트는 표시하지 않습니다.

### 9.4 접근성·반응형

- 모든 입력에 고유 ID와 label을 연결합니다.
- 로딩과 결과 갱신은 `aria-live`, 진행 단계는 적절한 상태 텍스트로 알립니다.
- 모바일 메뉴는 Escape 닫기, 포커스 이동·복귀, 모달 사용 시 포커스 제한과 배경 상호작용 차단을 지원합니다.
- 390px 화면에서 페이지 전체 가로 넘침이 없어야 합니다. 비교표는 모바일 카드로 전환합니다.
- reduced-motion 환경에서는 전환·펄스·쉐이더 움직임을 일관되게 줄입니다.
- WebGL 실패 시 정적 배경을 제공하며 검증 기능은 계속 사용할 수 있어야 합니다.

다음은 현재 파일과 인계서를 읽은 정적 검토 결과입니다. 이번 문서 작성에서 앱을 수정하거나 브라우저 재검증을 수행하지 않았습니다.

## 11. 기술 구성 제안

```text
Next.js 프론트엔드
  → 동일 출처 서버 API 경계
  → 검증 오케스트레이터
      → 입력·URL 검증 / 본문 추출
      → 주장 추출
      → 검색 공급자 adapter
      → 원문 수집 / 인용 검증 / 출처 그룹화
      → 조건 비교 / 판정 생성
      → 응답 무결성 검사
```

현재 활성 구조가 Next.js이므로 MVP에서 불필요한 프레임워크 전환은 하지 않습니다. 서버 API를 Next.js에서 구현할지 별도 FastAPI로 구현할지는 팀 역량과 기존 백엔드 유무에 따라 결정합니다. 별도 백엔드를 쓰더라도 브라우저에는 provider 키를 전달하지 않습니다.

### 제안 초기 제한값

| 항목 | 초기 제안 | 제한 도달 시 처리 |
|---|---|---|
| 입력 본문 | UTF-16 코드 단위 12,000개 | 자동 절단하지 않고 범위 축소 요청 |
| 확인 요청 | UTF-16 코드 단위 500개 | 입력 단계에서 안내 |
| 선택 주장 | 최대 3개 | 우선순위 선택 |
| 검색 | 주장당 최대 2회 | 검색 범위 한계 표시 |
| 원문 수집 | 실행당 최대 8개 URL 시도 | 추가 탐색은 후속 실행 |
| 외부 요청 | 요청별 15초 제한 | 실패 사유 기록, 가능한 나머지 처리 |
| 전체 작업 | 단계별 최대 90초 | 부분 결과 또는 시간 초과 반환 |
| 실패 재시도 | 일시적 오류에 한해 최대 1회 | 취소·예산 소진·접근 거절은 재시도하지 않음 |

모두 측정 전 설정 제안입니다. 서버와 클라이언트 검증 기준은 같아야 하며, 한글·이모지의 길이 정의 차이를 테스트합니다. provider 비용·호스팅 실행 제한에 맞춰 조정합니다.

## 12. API 계약 초안

현재 저장소에 아래 API가 구현되어 있다는 의미가 아닙니다. `HANDOFF.md`의 단일 `/api/fact-check` 제안보다 주장 선택과 장기 실행을 명시적으로 분리한 대체 초안입니다.

### 12.1 엔드포인트

| 메서드·경로 | 목적 | 결과 |
|---|---|---|
| POST `/api/analyses` | 입력 수집·주장 추출 작업 생성 | 202, analysisId와 queued 상태 |
| GET `/api/analyses/{analysisId}` | 추출 상태·원문·후보 조회 | 200, 준비되면 ready_for_selection |
| POST `/api/analyses/{analysisId}/runs` | 선택 주장으로 검증 실행 | 202, runId와 queued 상태 |
| GET `/api/runs/{runId}` | 진행·부분 결과·최종 결과 조회 | 200, 실행 상태와 revision |
| POST `/api/runs/{runId}/cancel` | 실행 취소 요청 | 202, cancelling 상태 또는 이미 종료된 상태 |

MVP에서는 polling을 사용하며 SSE는 후속 선택 사항입니다. POST에는 중복 클릭에 대비한 `Idempotency-Key`를 사용하고, 동일 키·다른 payload는 409로 거절합니다. 이 키와 불투명 ID만으로 접근을 허용하지 않으며 요청 세션의 소유권을 검사합니다.

### 12.2 입력 예시

```json
{
  "input": {
    "type": "text",
    "text": "여기에 사용자가 제공한 원문을 전달합니다."
  },
  "focus": "가격 변화의 비교 기간과 수치를 확인해 주세요."
}
```

URL 입력은 `input.type`을 `url`로, 값 필드를 `url`로 사용합니다. 둘을 동시에 받지 않습니다. HTML은 사용자 화면에 실행 가능한 형태로 넣지 않습니다.

검증 실행 요청:

```json
{
  "claimIds": ["claim-1"],
  "analysisRevision": 1
}
```

위 식별자는 계약 설명용 예시입니다. 서버는 주장 ID가 해당 분석 버전에 속하는지 검증합니다.

### 12.3 최소 데이터 모델

| 객체 | 필수 정보 |
|---|---|
| Analysis | id, revision, status, inputType, focus, normalizedText, claims, warnings |
| Claim | id, originalQuote, normalizedClaim, spans, type, checkability, conditions |
| Run | id, analysisId, analysisRevision, status, stage, revision, selectedClaimIds, createdAt, completedAt, results, errors |
| ClaimResult | claimId, status, verdict, summary, confirmed, unresolved, evidenceIds, warnings, checkedAt |
| Source | id, url, resolvedUrl, title, publisher, sourceType, role, publishedAt, retrievedAt, accessStatus, originGroupId |
| Evidence | id, claimId, sourceId, quote, locator, relation, comparisonConditions, quoteVerified |
| OriginGroup | id, sourceIds, basis, status |
| Error | code, stage, retryable, safeMessage, affectedClaimIds |

- 시각은 ISO 8601 UTC 형식으로 저장하고, 화면에서는 사용자의 시간대를 명시하여 표시합니다.
- 알 수 없는 발행일은 `null`로 두며 수집일로 추정하여 보완하지 않습니다.
- 판정이 없는 `verdict`는 `null`을 허용하며 처리 실패를 근거 부족으로 변환하지 않습니다.
- Evidence의 relation은 `supports / contradicts / context`, 원자료 관계의 status는 `confirmed / suspected / unknown`을 사용합니다.
- API 응답을 스키마로 검사하며 알 수 없는 enum이나 존재하지 않는 참조를 그대로 표시하지 않습니다.

### 12.4 원문 위치 규약

정규화는 줄바꿈의 LF 통일 등 필요한 최소한으로 제한하며, 정규화한 원문을 서버에서 반환합니다. `spans`는 해당 문자열에 대한 UTF-16 코드 단위의 시작 포함·끝 제외 범위인 `start`, `end` 객체의 배열입니다.

프론트엔드는 `normalizedText.slice(start, end)`와 인용의 일치 여부를 확인합니다. 불일치하면 잘못된 위치를 강조하지 않고 “원문 위치를 특정할 수 없습니다”라고 표시합니다. Python 구현에서는 일반 문자 인덱스를 그대로 사용하지 않고 UTF-16 기준으로 변환합니다.

### 12.5 오류 분류

`INVALID_INPUT`, `URL_BLOCKED`, `FETCH_DENIED`, `FETCH_TIMEOUT`, `EXTRACTION_FAILED`, `PROVIDER_UNAVAILABLE`, `RATE_LIMITED`, `SCHEMA_INVALID`, `CANCELLED`를 구분합니다. 429 응답은 재시도 가능한 시각을 안내하며 내부 예외·키·인증 헤더를 반환하지 않습니다.

## 13. 상태 관리와 비동기 실행

| 대상 | 상태 전이 |
|---|---|
| 원문·후보 추출 | queued → extracting → ready_for_selection / failed / expired |
| 검증 실행 | queued → running → completed / partial / failed |
| 취소 | queued 또는 running → cancelling → cancelled. 단, 먼저 완료된 경우 완료 상태 유지 |
| 주장 처리 | pending → running → completed / failed / cancelled |

`stage`는 검색·본문 수집·출처 정리·비교·결과 정리 단계를 나타냅니다. 처리 상태와 7개 판정은 별도 필드입니다. 실측하지 않은 퍼센트 대신 현재 단계와 완료한 주장 수를 표시합니다.

- `draftInput`, 제출된 스냅샷, `activeRunId`, `selectedClaimId`, 표시용 결과를 분리합니다.
- 응답의 runId와 revision을 확인하여 오래된 응답이 현재 결과를 덮어쓰지 않도록 합니다.
- 브라우저의 AbortController는 통신 중단 기능이며 서버 처리 중단을 보장하지 않습니다. 취소 API도 구현합니다.
- 취소 이후 늦게 도착한 결과가 화면을 완료 상태로 되돌리지 않는지 테스트합니다.
- 일부 주장만 실패하면 유효한 결과를 유지하고 실패한 주장과 이유를 구분하여 표시합니다.
- polling은 종료·취소·화면 이탈 시 중단합니다. 새로고침 시 복구는 저장 기간과 접근 권한 범위 안에서만 허용합니다.
- 서버리스 응답 이후 실행이 보장되지 않는 처리를 계속하지 않습니다. 로컬 상주 worker는 MVP 한정임을 명시하고 공개 환경에서는 영속 큐와 공유 상태 저장소를 사용합니다.

## 14. 보안·개인정보·이용 조건

### URL과 외부 콘텐츠

- URL은 HTTP/HTTPS만 허용하고 인증정보 포함 URL, 로컬·사설·링크로컬·클라우드 메타데이터 주소를 거절합니다.
- DNS 해석 이후 실제 연결 대상과 리다이렉트 대상을 매번 확인하며 IPv6·DNS 재해석을 통한 제한 우회도 방지합니다.
- 수집 크기·리다이렉트 횟수·시간·콘텐츠 형식을 제한합니다.
- HTML을 안전한 텍스트로 변환하고 인용에 포함된 스크립트나 이벤트 속성을 실행하지 않습니다.
- 외부 페이지의 프롬프트 주입으로 도구·권한·출력 정책이 변경되지 않도록 합니다.
- robots 정책, 사이트·검색 API 이용 조건, 인용 범위를 확인합니다. 로그인·유료벽·접근 제한은 우회하지 않습니다.

### 입력·저장

- API 키는 서버 환경변수·secret 관리에 보관하고 브라우저 공개 변수나 Git에 포함하지 않습니다.
- 입력이 외부 검색·LLM으로 전송된다는 사실을 전송 전에 안내합니다. 검색에는 필요한 주장만 사용하고 전문 전송을 최소화합니다.
- 이름·주소·전화번호 등이 포함된 입력에는 삭제·마스킹을 안내합니다.
- MVP 제안은 “로그인 없음·비공개·단기 세션 저장”입니다. 서버의 입력·결과는 24시간 이내에 만료·삭제하는 설계를 후보로 둡니다. 정식 운영 전에 로그·백업까지 포함하여 보장할 수 있는지 확인합니다.
- 외부 provider의 보존 조건은 별도로 확인하며, 확인 전에 “검증에만 사용”, “완전 비저장”을 단언하지 않습니다.
- 원문 전체를 운영 로그에 기록하지 않으며 요청 ID·단계·소요 시간·오류 유형을 중심으로 기록합니다.
- MVP에서는 공개 공유와 제3자 열람을 제공하지 않습니다.
