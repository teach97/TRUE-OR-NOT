## 0. 한눈에 보기

**제품 정의.** True or Not은 정답을 선언하는 서비스가 아니라, 주장과 근거를 추적·비교할 수 있게 하는 생활형 검증 도구입니다. 사용자가 제공한 기사·댓글·텍스트에서 확인할 주장을 추출하고, 원문과 검색 근거를 함께 제시하며, 확인된 것과 불확실한 것을 구분합니다.

**현재 상태.** 텍스트·링크·이미지 입력 → 주장 추출 → 검색 → 원문 읽기 → 판정 → AI 개요 합성의 5단계 파이프라인이 로컬 환경에서 동작합니다. 실제 provider 호출로 전체 경로를 확인한 기록이 있으며(인계서), 브라우저 취소·장애 복구·데모 분리 회귀도 통과한 것으로 기록되어 있습니다.

**시연 전제.** 프록시가 production 빌드의 POST를 항상 거부하고 백엔드 주소를 loopback으로 고정하므로, 현재 시연은 로컬 개발 서버에서만 가능합니다. 공개 배포는 지원하지 않습니다.

**우선 확인이 필요한 한계 (상세는 14절).**

| 우선 | 한계 |
|---|---|
| 높음 | JEV 빠른 경로가 입력 전체를 하나의 사실 주장으로 고정하여 의견·예측도 사실로 판정할 수 있음 (L1) |
| 높음 | 동시 실행 제한이 메인 스트림 프록시에만 있어 jev·intent·백엔드 단독 호출은 제한이 없음 (L2) |
| 높음 (확인 필요) | 링크 단독·이미지 단독 입력에서 결과 조립 단계의 재검증이 실패할 가능성 (L3) |
| 중간 | 합성 생략·실패·JEV 모드가 모두 "근거 부족" 답변으로 표시됨 (L4) |
| 중간 | 인계서와 기획서가 실제 코드와 어긋난 부분이 있음 (L8) |

**팀 결정이 필요한 사항 (상세는 16절).** 점수 표시 정책, JEV 경로 정책, 후보 선택 UI 도입, 이미지 입력의 공식 범위 편입, 배포 범위, Finnhub 연결 여부.

## 1. 핵심 방향

**True or Not은 정답을 선언하는 서비스가 아니라, 주장과 근거를 추적·비교할 수 있게 하는 생활형 검증 도구입니다.**

- 도메인: 생활·문화 중심의 일반 정보
- 대상: 기사와 온라인 주장에 의문을 가진 일반 사용자
- 핵심 단위: 기사 전체가 아닌 개별 주장
- 핵심 산출물: 원문 위치와 출처 인용이 연결된 주장별 검증 카드
- 성공 경험: 사용자가 판정 문구만 읽는 것이 아니라 근거를 열고 결론의 한계를 이해합니다.
- 비목표: AI 판정 정확도의 무근거 수치화, 작성자 평가, 전문 의사결정 대행

## 2. 문제 정의와 사용자 시나리오

온라인 텍스트에는 사실, 의견, 예측, 과장 및 오래된 정보가 섞여 있습니다. 여러 기사가 검색되어도 같은 발표를 재인용한 경우 독립적인 근거가 늘어난 것은 아닙니다. 수치가 다르더라도 비교 기간·지역·모집단 차이일 수 있으므로 불일치 자체를 오류로 단정하지 않습니다.

| 사용자 상황 | 확인하려는 질문 | 제공할 결과 |
|---|---|---|
| 생활 물가 기사 | 어느 상품이 언제부터 얼마나 올랐는가? | 기간·대상·단위가 맞는 통계와 비교 |
| 정책 관련 댓글 | 확정된 정책인가, 검토 중인 안인가? | 발표일·시행일·정책 상태 구분 |
| 문화 행사 정보 | 올해 일정인가, 지난 행사 기사인가? | 행사 연도·지역·공식 공지 비교 |
| 과장된 온라인 문장 | 사실 부분과 해석이 무엇인가? | 사실 주장과 의견을 분리하고 한계 제시 |

의학·법률·투자의 개인별 판단 요청은 범위 밖입니다. 사용자의 상태에 대한 진단이나 매매·법률 행동 권고를 생성하지 않습니다.

## 3. 제품 원칙

1. 검색 결과 부재를 거짓의 증거로 사용하지 않습니다.
2. AI가 생성한 설명을 원문 인용처럼 표시하지 않습니다.
3. 출처 개수와 독립적인 근거 수를 혼동하지 않습니다.
4. 공식 출처라는 이유만으로 모든 주장을 무조건 확인 처리하지 않습니다. 해당 주장과 직접 관련되는지 확인합니다.
5. 판정마다 기준 시각과 자료의 범위를 명시합니다.
6. 판정 근거가 부족하면 결론을 유보합니다.
7. **(v3에서 수정)** 주장별 점수(0~100)는 LLM·JEV 판정의 부가 지표이며 단독 진실값이 아닙니다. 종합 평균과 출처 품질 퍼센트는 표시하지 않습니다. 이 정책은 잠정안이며 D1에서 확정합니다.
8. 데모와 실제 검증을 입력·결과·다운로드에서 모두 구분합니다.
9. 입력 내용과 수집 페이지는 데이터로 취급하며, 그 안의 지시문을 도구 실행 지침으로 따르지 않습니다.
10. 접근 차단·로그인·유료벽은 우회하지 않고 대체 입력 경로를 제공합니다.
11. **(v4 추가)** 검색 스니펫, LLM 검색 요약, 유튜브 제목·댓글은 인용 근거로 쓰지 않습니다. 원문 읽기와 인용 검증을 통과한 문구만 근거와 AI 개요에 사용합니다. [인계서]
12. **(v4 추가)** 처리 생략·처리 실패를 "근거 부족"으로 표시하지 않습니다. 현재 구현은 이 원칙을 완전히 지키지 못하며 L4로 관리합니다.

## 5. 실제 사용자 흐름

1. **입력**: 텍스트, 링크, 이미지 중 하나 이상과 선택적 확인 요청을 입력하고 외부 전송에 동의합니다.
2. **인텐트 게이트**: 짧은 입력이나 질문은 검증 없이 답변하고, 검증 대상이면 파이프라인을 시작합니다. [코드: `/api/intent`]
3. **추출**: 최대 3개 주장을 추출합니다. 링크만 입력한 경우 서버가 페이지 본문을 수집하여 추출하며, 이 경우 검증 대상 본문이 입력 텍스트를 대체합니다.
4. **검색**: Tavily 또는 LLM 웹검색으로 후보 출처를 찾습니다. 링크가 있으면 링크 원문을 첫 출처로 두고 링크 제목 기반 관련 기사를 추가합니다.
5. **읽기**: 후보 출처의 원문을 수집합니다. 접근 실패는 근거로 만들지 않고 접근 불가로 표시합니다.
6. **검증**: 인용과 참조 무결성을 검사하고 주장별로 판정합니다.
7. **합성**: 검증된 원문 인용으로 AI 개요를 만듭니다. 합성이 불가능하면 고정 안내 문구를 표시합니다.
8. **결과·재시도**: 결과 카드에서 근거를 열어보고, 필요하면 취소·재시작·JSON 내보내기를 합니다.

사용자 선택 단계는 현재 없습니다. 실행 중에는 동시에 한 건만 처리하며, 진행 중 요청이 있으면 BUSY로 거절합니다.

## 6. 주장 추출과 검증 계획

### 6.1 분류 체계

문장 유형과 검증 가능 여부를 분리합니다.

| 유형 | 처리 |
|---|---|
| 사실 주장 | 시점·대상·범위가 충분하면 검증 |
| 의견·가치 판단 | 검증 대상 아님. 포함된 사실 요소는 별도 주장으로 추출 가능 |
| 예측 | 미래 결과는 현재 확정하지 않음(`not_checkable` 유지). 전망 출처는 검색·합성 대상 |
| 풍자 | 문맥이 분명할 때만 표시. 불명확하면 유형을 미확정으로 둠 |
| 유형 불명확 | 사용자에게 대상·기간 등 추가 조건 요청 |

사실 주장이지만 검색 근거가 없는 경우에는 "검증 대상 아님"이 아니라 "근거 부족"입니다. **JEV 빠른 경로는 이 분류를 거치지 않으므로 L1로 관리합니다.**

### 6.2 주장 구조

주장별로 주체, 서술, 대상, 수치, 단위, 기간, 지역, 비교 기준을 구조화합니다. 원문에 없는 조건은 만들어 넣지 않으며, '최근'·'올해' 같은 상대 시점은 기사 발행일 등 해석 기준을 명시합니다.

- 추출 주장은 원문의 의미를 보존하며, 원문 범위를 벗어난 후보는 조용히 제외합니다. [인계서]
- 확인 요청은 추출 필터가 아니라 우선순위 신호로 사용합니다. 원문에 확인 가능한 주장이 있으면 세부 조건이 없어도 먼저 추출하고, 이후 단계에서 근거 부족을 판정합니다. [인계서 2026-09-22]
- 후보가 많으면 확인 요청과 관련성이 높은 주장을 우선하되 일부만 분석했다는 사실을 표시합니다.

### 6.3 검색 계획

주장별 검색어는 추출 단계에서 함께 생성하며(개체·날짜·숫자·부정 표현 보존), 별도 LLM 호출을 추가하지 않습니다. [인계서] 예측 질문도 검색 대상에 포함하고 의견은 제외합니다. 검색 결과는 공급자가 반환한 후보 순서를 보존하며, 이 순서는 Google 자연검색 순위가 아닙니다. 모든 검색 공급자 결과에서 일본어 문서(.jp 도메인, 제목·요약의 가나, 원문 읽기 후 일본어 본문 판별)를 제외하며, 영어 페이지가 .jp 도메인을 쓰는 경우도 제외될 수 있습니다. [인계서]

## 7. 출처 정책과 독립성

| 출처 유형 | 역할 | 주의점 |
|---|---|---|
| 정부·공공기관·공식 통계 | 정책·수치의 주요 근거 후보 | 조사 범위·개정 여부·공표일 확인 |
| 논문·연구기관 보고서 | 전문 주장에 대한 근거 후보 | 연구 대상·방법·한계 확인 |
| 공식 발표·인터뷰·원문 기사 | 사건·발언의 직접 자료 | 발언 사실과 발언 내용의 진실성을 구분 |
| 관련 기사 | 비교·추가 탐색 | 원자료 인용과 독자 취재를 구분 |
| 위키피디아·나무위키 | 배경·검색 확장 | 핵심 판정의 단독 근거로 사용하지 않음 |
| 블로그·커뮤니티·댓글 | 유통 주장·경험·반응 확인 | 일반화의 근거로 사용하지 않음 |
| 유튜브 영상 제목·공개 댓글 | 의견 맥락 표시 | 판정·인용·AI 개요 근거로 사용하지 않음 |

출처 유형과 역할은 별개입니다. 검증 대상 기사도 직접 인터뷰의 원자료일 수 있으며, 공식 발표도 이해관계자의 주장일 수 있습니다.

### 독립성 처리 (현재 구현 기준)

1. 추적 파라미터(`utm_*`, `fbclid`, `gclid`, `msclkid` 등)와 `www`·끝 슬래시·쿼리 순서를 정규화하여 문서 중복을 제거하고, 원문 읽기 뒤 리다이렉트 최종 URL도 비교합니다. 문서 ID·동영상 ID 등 의미 있는 쿼리는 유지합니다. [인계서]
2. 같은 사이트의 출처는 최대 2개, 전체는 최대 6개로 제한합니다. 이 제한은 독립성이나 신뢰도를 보장하는 규칙이 아닙니다. [인계서]
3. `originGroupId`는 URL 기준으로 부여되며(`origin_group_for_url`), 공통 인용문·명시적 원자료 링크에 기반한 계보 확인은 구현되어 있지 않습니다. [코드]
4. 따라서 결과에는 "출처 간 독립성과 원자료 계보는 확인되지 않았습니다" 경고가 항상 표시됩니다. [코드]
5. "확인된 원자료 그룹 수" 지표와 계보 분석은 후속 과제이며, 출처 수를 독립 근거 수로 부르지 않습니다.

## 8. 판정 정책

### 8.1 결과 분류

| 코드 | 표시명 | 적용 기준 |
|---|---|---|
| mostly_supported | 대체로 확인됨 | 핵심 사실과 비교 조건이 직접 관련된 원문 근거와 일치하며 중대한 미해결 반박이 없음 |
| partially_supported | 일부만 확인됨 | 복합 주장의 일부만 확인되거나 일부 조건이 미확정 |
| missing_context | 맥락이 생략됨 | 표현 자체는 맞지만 조건·기간·범위 생략으로 의미가 달라짐 |
| conflicting_sources | 출처 간 내용이 다름 | 동일 조건으로 비교해도 관련 근거가 충돌하고 해소되지 않음 |
| insufficient_evidence | 근거 부족 | 직접 근거 미확보, 조건 불명확 또는 검색 범위 내 판단 불가 |
| not_checkable | 검증 대상 아님 | 의견·가치 판단·현재 확정할 수 없는 예측 등 |
| contradicted | 반박하는 근거 확인 | 같은 조건의 직접 근거가 핵심 주장을 반박하고 중대한 미해결 충돌이 없음 |

위 코드는 v3 정책 기준이며 `contracts.py`·`verification.py`와의 대조는 [확인 필요]입니다.

### 8.2 겹치는 경우의 결정 규칙

- 먼저 사실 검증 대상인지 확인합니다.
- 핵심 비교 조건을 맞출 수 없거나 유효 인용이 없으면 근거 부족으로 처리합니다.
- 기간·지역·단위를 맞추면 해소되는 차이는 출처 충돌로 단정하지 않습니다.
- 같은 조건의 유효 근거가 지지·반박으로 갈리면 충돌을 우선 표시하고 양쪽을 제시합니다.
- 중요한 조건 생략이 문제의 핵심이면 맥락 생략을 적용합니다.
- 복합 주장은 가능하면 분리하고, 분리 전 요약에는 일부 확인과 하위 결과를 제공합니다.
- 핵심 내용이 직접 반박되면 주변 사실 일부가 맞더라도 전체를 확인됨으로 처리하지 않습니다.

대표 판정은 하나만 사용하고 `warnings`에 조건 미확정·원자료 미확보·독립성 미확인 등을 함께 제공합니다. 판정은 정책 초안이며 QA 사례로 모호한 경계를 조정해야 합니다.

### 8.3 근거 충족 규칙

- 확인·부분 확인·맥락 생략·반박에는 실제 수집 원문에서 검증된 인용을 최소 하나 연결합니다. 이는 최소 형식 조건이며 하나의 출처만으로 충분한지는 주장별로 판단합니다.
- 충돌 판정에는 상충하는 근거와 같은 조건으로 비교했다는 설명이 필요합니다.
- 검색 스니펫만 확보한 문서는 발견한 자료로 표시하며 결정적 원문 근거로 사용하지 않습니다.
- 원문에 없는 인용, 인용 대상 URL 불일치, 의미가 달라지는 문맥 절단이 발견되면 해당 근거를 제외하고 판정을 재평가합니다.
- 생성된 판정은 서버의 스키마·인용·참조 무결성 검사를 통과해야 노출합니다. [인계서: `quoteVerified: true`와 claim·source·evidence 교차 참조 검증]
- 본문 추출은 메뉴·사이드바·푸터·플레이어 등 화면 UI 문구를 제외하며, 그런 문구는 인용으로 통과하지 못합니다. [인계서]

### 8.4 점수와 판정의 관계 (잠정)

- 주장별 점수는 판정을 대체하지 않는 부가 지표입니다. 점수와 판정이 어긋나면(예: 높은 점수인데 근거 부족) 판정과 경고를 우선 표시하고 점수는 접거나 보조로 표시합니다. [제안, D1]
- JEV 판정은 점수 중심 결과이며 AI 개요를 만들지 않습니다. JEV 경로로 얻은 결과임을 결과 화면에 표시해야 합니다. 현재 결과의 `model` 필드는 `jev-latest`로 기록됩니다. [코드]

## 9. 화면 설계

### 9.1 현재 확인된 구현 [인계서]

- 한국어 다크 UI, 진행 단계 표시, 사용자 취소와 재시작, 오류 후 같은 화면 재시도
- 주장 카드: 판정, 요약, 근거 관계, 확인된 내용, 주장별 주의사항, 발행일 미확인 표시, 전체 검증 한계
- 주장을 선택하면 해당 주장의 인용과 출처만 근거 패널에 표시되고, 근거가 없는 주장은 "근거 없음"으로 표시
- AI 개요: 조건부 전망·불확실성·정리 섹션과 인라인 출처 칩. verified 비-유튜브 출처이며 안전한 HTTP(S) URL인 경우에만 새 탭 링크를 제공하고, 동일 출처는 첫 링크를 가리키는 번호 참조로 표시
- 합성이 불가능할 때는 AI가 생성한 답처럼 보이지 않도록 고정 안내 문구 표시
- 유튜브 패널: 영상 제목·채널·게시일·조회수와 공개 댓글(최대 10개). 댓글 왼쪽 프로필 그림은 로컬에서 만든 합성 이미지이며 실제 작성자 정보는 요청하지 않음
- 독립 데모: 실제 백엔드를 호출하지 않으며 결과·내보내기에 `demo=true`로 표시
- JSON 내보내기: `demo`, claim·source·evidence 참조 포함. 유튜브 API 데이터는 제외
- 개인정보 처리방침·이용약관 페이지 초안 (운영자 정보·법적 검토 미완)

PNG 화면 캡처는 인계서 체크리스트에 있으나 `package.json`에 관련 의존성(html2canvas)이 없어 현재 제공 여부를 [확인 필요]로 둡니다.

### 9.2 설계 지침 (v3 유지, 검증 수준은 별도 표기)

- 원문의 노란 강조는 "선택된 검증 대상"을 뜻하며 판정 색상과 구분합니다. 색만 사용하지 않고 문장 유형·판정 텍스트·아이콘을 병행합니다.
- 근거에는 원문 그대로의 인용과 별도로 작성한 해설, 지지·반박·배경 관계, 수치·단위·기간·지역 및 비교 기준, 출처 제목·기관·URL·발행일·수집 시각, 원자료 그룹 또는 관계 미확인을 함께 표시합니다.
- 요약 지표는 현재 실행 결과에서만 집계하고, 정규화된 식별자로 문서를 중복 제거합니다. 처리 실패와 근거 부족은 다른 지표입니다. 평균 신뢰도와 출처 품질 퍼센트는 표시하지 않습니다.
- 모든 입력에 고유 ID와 label을 연결하고, 로딩·결과 갱신은 `aria-live`로 알립니다. 390px 화면에서 페이지 전체 가로 넘침이 없어야 하며, reduced-motion 환경에서는 전환·펄스·쉐이더 움직임을 줄입니다. WebGL 실패 시에도 검증 기능은 계속 사용할 수 있어야 합니다.

```text
  → Next.js route (로컬 전용 프록시)
      /api/fact-check (GET 상태, POST 스트림), /api/fact-check/jev, /api/intent
      → FastAPI (backend/main.py, 127.0.0.1:8010)
          → LangGraph 5단계: 추출 → 검색 → 읽기 → 검증 → 합성
          → 결과 조립·계약 검증 → NDJSON 스트림
```

브라우저에는 provider 키를 전달하지 않습니다. 프록시는 백엔드 주소를 `127.0.0.1` 또는 `[::1]`의 루트 경로로만 허용하고 리다이렉트를 거부합니다. [코드]

### 10.2 엔드포인트

| 메서드·경로 | 위치 | 목적 |
|---|---|---|
| GET `/health` | FastAPI | 프로세스 생존과 git 리비전 |
| GET `/api/fact-check` | FastAPI, 프록시 | 워크플로 준비 여부, 모델 옵션, JEV 설정 여부 |
| POST `/api/fact-check` | FastAPI | 단일 JSON 응답. 프록시는 이 경로를 쓰지 않음 |
| POST `/api/fact-check/stream` | FastAPI, 프록시(`/api/fact-check` POST) | NDJSON 진행·결과·오류 이벤트. 주 경로 |
| POST `/api/fact-check/jev` | FastAPI, 프록시 | JEV 빠른 경로 |
| POST `/api/intent` | FastAPI, 프록시 | 검증 실행과 단순 답변 구분 |

v3가 제안한 `analyses`·`runs`·`cancel` 분리 API는 구현하지 않았습니다. 후보 선택 단계(D3)를 도입할 때 다시 검토합니다. 취소는 별도 API가 아니라 스트림 연결 종료가 백엔드 작업 취소로 전파되는 방식입니다. [인계서 검증]

### 10.4 결과 계약 (`FactCheckResult`) [코드]

`text`, `focus`, `demo`, `model`, `reasoning`, `checkedAt`, `claims`, `sources`, `evidence`, `warnings`, `answer`.

출처(source) 공개 필드: `id`, `url`(리다이렉트 최종 URL 우선), `title`, `publisher`, `publishedAt`, `retrievedAt`, `accessStatus`(`verified`·`unavailable`), `sourceType`, `originGroupId`, `searchProvider`, `searchQuery`, `candidateOrder`, 유튜브 관련 필드. 발행일을 알 수 없으면 `null`을 유지합니다.

v3의 Analysis·Run·ClaimResult 분리 모델은 현재 구조에서는 사용하지 않습니다. 실행 식별자(`runId`)와 revision이 없으며, 스트림이 한 번의 실행에 대응합니다.

### 10.7 오류 코드

| 코드 | 발생 위치 | 의미 |
|---|---|---|
| INVALID_REQUEST | 프록시(400), 백엔드(422) | 입력·동의·형식 오류. 원인 필드는 구분하지 않는 공통 문구 |
| LOCAL_ONLY | 프록시(403) | 로컬 동일 출처가 아닌 요청 또는 production |
| BUSY | 프록시(429) | 진행 중인 검증이 있음 |
| CANCELLED | 프록시(400) | 요청이 취소됨 |
| NOT_CONFIGURED | 백엔드(503) | provider 또는 JEV 설정 없음 |
| AGENT_FAILED | 백엔드(502) | 검증 실패 (내부 진단은 노출하지 않음) |
| BACKEND_UNAVAILABLE / BACKEND_FAILED | 프록시(503/502) | 백엔드 연결 불가 / 백엔드 오류 |
| TIMEOUT | 프록시(504) 또는 스트림 이벤트 | 검증 시간 초과 |
| INTENT_FAILED | 프록시(503) | 의도 파악 실패 |
| LOW_CONFIDENCE, GATEWAY_ERROR, NO_JUDGMENT, BAD_RESPONSE | JEV 경로(502) | JEV 판정 실패 유형 |

v3의 `URL_BLOCKED`, `FETCH_DENIED`, `RATE_LIMITED` 등은 공개 코드로 구현되어 있지 않습니다. 단계별 내부 오류(`EXTRACTION_FAILED`, `SEARCH_FAILED`, `VERIFICATION_FAILED`, `SYNTHESIS_FAILED` 등)가 스트림에서 어떤 공개 코드로 전달되는지는 `streaming.py` [확인 필요]입니다.

### 10.8 원문 위치 규약

`spans`(주장의 `start`·`end`)는 정규화된 원문에 대한 UTF-16 코드 단위 범위(시작 포함, 끝 제외)입니다. 코드에서 JEV 경로의 주장 범위가 UTF-16 기준으로 계산됨을 확인했습니다. 프론트엔드가 `normalizedText.slice(start, end)`와 인용의 일치를 검사하고, 불일치 시 잘못된 위치를 강조하지 않는 처리는 [확인 필요]입니다.

## 11. 상태 관리와 비동기 실행

| 대상 | 현재 방식 |
|---|---|
| 실행 단위 | 한 번의 POST가 한 번의 스트림 실행. `runId`·revision 없음 |
| 진행 | NDJSON 이벤트로 단계 진행, 최종 결과, 오류 전달. 실측하지 않은 퍼센트는 표시하지 않음 |
| 취소 | 브라우저 취소·문서 이탈 → 프록시가 upstream fetch·reader 취소 → FastAPI 스트림·그래프 취소 [인계서 검증] |
| 동시성 | 프록시 프로세스별 1건. 초과 요청은 429 BUSY. 취소·실패 뒤 재시작이 BUSY에 걸리지 않음을 검증 [인계서] |
| 오래된 응답 | 스트림 1연결 구조라 별도 revision 검사가 없음. 취소 후 늦게 도착한 결과의 화면 처리는 [확인 필요] |
| 장애 | 백엔드 연결 불가는 사실 판정이 아닌 실패로 표시하고 같은 화면에서 재시도 가능 [인계서] |
| 저장 | 서버 영속 저장 없음. 상태는 프로세스 메모리에 한정 |

실제 provider 내부 취소와 과금 중단, 실행 중 서버 강제 종료의 모든 조건은 보장하지 않습니다. [인계서]

- 주요 API 계약·인용 참조·원문 범위·비동기 상태에 자동 테스트가 있어야 합니다.
- Q01~Q18의 실행 결과·기대값·실패·미확인 상태를 기록해야 합니다.
- 보안 경계, 입력 혼동, 실재하지 않는 인용 문제는 출시를 중단하는 결함으로 취급합니다.
- 공개 가능한 시료로 검색·LLM 실제 연결을 최소 한 번 검증하고 fixture 시험과 구분해야 합니다. 실제 연결이 불가능하면 데모로 제출하고 실제 검증이 동작했다고 보고하지 않습니다.
- 측정 전의 "정확도 ○%"는 홍보하지 않습니다. 측정 후보는 인용 정합성, 원문 위치 일치, 판정과 사람 평가의 차이, 처리 시간, 실행당 비용입니다.

## 19. 팀 적용 보완 (2026-09-30)

v3식 역할 4분할(에이전트/검색/프론트/QA) 대신 파일 소유권 기준 A~D 배치를 채택한다. Python 백엔드에 작업이 몰려 있어 충돌이 적다.

| 역할 | 담당 파일 |
|---|---|
| A. 프론트·프록시 | 화면 컴포넌트, 클라이언트, route.ts 3종 |
| B. 검증 엔진 | extraction.py, verification.py, jev.py, answer_synthesis.py, scoring.py |
| C. 검색·수집·조립 | search.py, sources.py, tavily_search.py, youtube.py, providers.py, runtime.py, main.py, streaming.py |
| D. 계약·QA·문서 | contracts.py, schemas.py, 테스트 전체, 인계서·기획서 |

- 계약이 경계선이다. contracts.py 변경은 누구나 하되 D가 수 시간 내 리뷰하고, CI 계약 테스트가 안전망이다. D8·D1 변경은 D 승인 하에 A·B가 함께 리뷰한다.
- providers.py는 전 단계가 쓰는 공통 인프라이므로 합류점 소유자인 C가 맡는다.
- runtime.py는 C 소유, B와 겹치는 변경은 B 리뷰를 받는다.
- 유료 호출은 D만 실행한다.
- L14 이후 번호의 작업 지시는 v4(L1~L13)에 존재하지 않는다. 배정 전 대조 확인이 필요하며, L15(중복 인용)는 해소된 것으로 본다.
- A~D 실명 배정은 팀원 강점(프론트·백엔드 경험, 문서·발표 강점) 확인 후 정한다.
